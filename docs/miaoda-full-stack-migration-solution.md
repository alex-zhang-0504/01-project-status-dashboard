# 项目状态看板妙搭全栈迁移方案

## 文档定位

本文是项目状态看板迁移到飞书妙搭全栈应用的固定学习与实施方案，用于后续复习、交接和判断变更是否偏离已确认路线。

- 稳定的目标、架构、仓库边界和验收原则维护在本文。
- 可跨 Project 复用的本地开发、App Git、妙搭发布、线上验收与故障分层规则维护在项目根目录 `MIAODA_LOCAL_TO_ONLINE_RULES.md`。
- 实际进度、阻塞、提交、发布和验证结果维护在 `ROADMAP.md`。
- 当前本地正式基线为 `V1.2.0`；具体版本提交以父 Git 最新提交为准。
- 迁移开发期只由应用创建者验证，不添加协作者或其他操作者；团队验证延后至 2026 年 8 月第一周。

## 一、为什么迁移

当前看板已经能从三个飞书多维表格数据源生成正式单文件网页，但运行依赖指定电脑、Python、`lark-cli` 用户登录态和本地启动脚本。每周会议前仍需要由固定人员启动、刷新并准备看板，无法把日常使用责任交给其他负责人。

迁移目标不是重做看板，而是把运行责任从个人电脑转移到妙搭托管环境：负责人只维护 Base，之后直接打开应用并刷新看板；维护者只在字段、统计或样式变化时介入。

## 二、妙搭全栈应用是什么

对本项目而言，全栈应用由三层组成：

```text
浏览器前端
展示图表、表格、切换视图、点击刷新
        ↓
妙搭服务端
安全读取 Base，执行筛选、解析、统计和错误处理
        ↓
飞书多维表格
继续作为唯一业务事实来源
```

### 前端

前端对应当前 `src/template-dashboard-v1.2.0.html` 的页面能力，包括项目概况、详细进展、遗留问题、创新大赛、PM 切换、全屏、重新生成和离线快照下载。

迁移时复用当前视觉规范、页面结构和数据契约，不让妙搭 AI 从零重写设计。

### 服务端

服务端对应当前 `generate_dashboard.py` 和 `serve_dashboard.py` 的职责：

- 只读访问三个 Base 数据源。
- 按「是否上周三例会」筛选记录。
- 解析最新进展、控制点、风险、状态和日期。
- 计算项目概况、开发达成率和问题周次。
- 向前端返回结构化数据。
- 隐藏应用身份、Base 标识和其他运行配置。

浏览器不能安全保存应用凭据，因此需要妙搭服务端，不能只发布静态 HTML。

### 平台层

妙搭负责应用托管、发布、运行时访问范围、环境变量、日志、调用链和后续协作。应用开发协作者与普通使用者是两套权限：前者维护代码，后者只打开发布后的应用。

## 三、目标架构

```text
进展 Base ──────┐
问题 Base ──────┼─→ 妙搭服务端只读适配层 ─→ 看板数据契约 ─→ V1.2.0 前端
创新大赛 Base ─┘
```

核心决策：

1. 创建 `full_stack` 妙搭应用。
2. 采用本地代码开发，不采用妙搭云端 AI 重写。
3. Base 继续作为唯一业务事实来源，不同步到妙搭数据库。
4. 开发期不提供 Base 回写能力。
5. 三个数据表统一使用 Base OpenAPI，不混用妙搭官方多维表格插件；官方插件无法读取正式契约依赖的 Lookup 字段「阶段查找／状态查找」。
6. 服务端使用独立飞书应用的 `tenant_access_token`，不依赖任何个人电脑上的 `lark-cli` 登录态；目标 Base 须单独向该应用授予足够的文档／高级权限。
7. 迁移验收前保留本地 `V1.2.0`，并继续保留 `V1.1.0` 模板作为应急回退方案。

## 四、本地方案与妙搭方案横向对比

| 对比项 | 当前本地方案 | 妙搭全栈方案 |
|---|---|---|
| 运行位置 | 指定 Windows 电脑 | 妙搭托管环境 |
| 启动方式 | 双击 `start-dashboard.cmd` | 应用持续在线 |
| 前端 | 单文件 HTML 模板 | 复用现有模板并适配妙搭 |
| 服务端 | 本地 Python | 妙搭托管服务端代码 |
| Base 身份 | `lark-cli` 用户登录态 | 独立飞书应用身份，Base 单独授权 |
| 数据源 | 三个 Base | 相同的三个 Base |
| 业务计算 | `generate_dashboard.py` | 迁移到妙搭服务端 |
| 刷新接口 | 本机 `/api/data` | 妙搭云端接口 |
| 使用入口 | 本地页面或离线 HTML | 仅授权用户可访问的应用链接 |
| 日常准备 | 需要固定人员启动和刷新 | 负责人自行打开和刷新 |
| 维护交接 | 需要配置本地环境 | 加入妙搭协作后维护应用 |
| 离线快照 | 每次成功刷新自动写入本地 | 按需在浏览器下载，不在服务端永久存储真实数据 |
| 日志 | 本地终端 | 妙搭线上日志和调用链 |
| 回退 | 当前运行方式 | 回退到保留的本地 `V1.2.0`，必要时可切回 `V1.1.0` 模板 |

## 五、运行步骤的一一对应关系

| 阶段 | 当前本地方案 | 妙搭全栈方案 | 迁移性质 |
|---|---|---|---|
| 1. 维护数据 | 负责人填写 Base | 负责人填写 Base | 不变 |
| 2. 启动环境 | 固定人员启动本地脚本 | 妙搭应用保持在线 | 平台替代 |
| 3. 取得身份 | 读取个人 `lark-cli` 登录态 | 服务端获取 `tenant_access_token` | 重做 |
| 4. 读取 Base | Python 调用 `lark-cli` | 服务端统一调用 Base OpenAPI 查询三张表 | 重做 |
| 5. 解析和统计 | Python 执行业务规则 | 妙搭服务端执行相同规则 | 逻辑迁移 |
| 6. 生成页面数据 | Python 生成 JSON | 妙搭接口返回 JSON | 保持契约 |
| 7. 渲染看板 | HTML 模板渲染 | 复用模板渲染 | 高度复用 |
| 8. 会议中刷新 | 点击按钮访问本机接口 | 点击按钮访问云端接口 | 交互不变 |
| 9. 生成离线文件 | 自动写入 `output/` | 用户按需下载当前快照 | 明确调整 |
| 10. 交给负责人 | 固定人员准备页面或转发文件 | 负责人直接打开应用 | 核心收益 |

## 六、仓库管理方案

### 管理结论

迁移仍属于当前业务 Project，但妙搭运行代码使用独立 Git 仓库：

- 父 Git 管理产品方案、项目规范、路线图、本地 `V1.2.0`、旧版本模板和妙搭版本档案。
- App Git 管理妙搭前端、服务端、依赖和应用提交历史。
- 妙搭远端 Git 接收 App Git 的 `sprint/default` 提交，并作为发布代码来源。

```text
01-project-status-dashboard/
├─ src/                              # 父 Git：本地 V1.2.0 与旧版本模板
├─ tests/                            # 父 Git：本地回归
├─ docs/                             # 父 Git：方案与说明
├─ deployments/
│  ├─ miaoda-app.json                # 父 Git：非敏感版本档案
│  └─ miaoda-app/                    # App Git：妙搭源码
│     ├─ .git/
│     ├─ .spark/
│     └─ ...
├─ AGENTS.md
├─ README.md
└─ ROADMAP.md
```

### 为什么父 Git 忽略 App 源码

妙搭 App 仓库使用 `sprint/default` 作为开发分支，发布成功后由平台推进 `main`；父工作区使用自己的 `main／release` 规则。父 Git 若再次管理 App 源码，会形成两个仓库同时声明同一批文件，容易误提交或产生错误发布判断。

父仓库的 `.gitignore` 必须包含：

```gitignore
/deployments/miaoda-app/
```

这条规则只阻止父 Git 接管 App 源码，不会删除本地文件，也不会影响 App 内部的 `.git`。

### 防止误提交的三道防线

1. `deployments/miaoda-app/.git` 是独立仓库；在 App 目录执行 Git 时自动命中它。
2. 父仓库通过 `.gitignore` 忽略整个 App 目录。
3. App Git 命令统一使用 `git -C deployments\miaoda-app ...`，显式指定仓库。

提交前必须核对：

```powershell
git -C deployments\miaoda-app rev-parse --show-toplevel
git -C deployments\miaoda-app status --short
git status --short -- .
```

禁止使用 `git add -f` 强行把 App 源码加入父 Git；禁止删除 App 的 `.git` 后继续提交。

### 改动如何归档

```text
本地修改 App
→ 提交到本地 App Git
→ push 到妙搭远端 sprint/default
→ 创建妙搭发布
→ 记录 commit SHA 和 release ID
→ 更新父 Git 的 miaoda-app.json 与 ROADMAP.md
```

查询 App 源码历史：

```powershell
git -C deployments\miaoda-app log --oneline --decorate --graph -20
git -C deployments\miaoda-app show <commit_sha>
git -C deployments\miaoda-app diff
```

查询妙搭发布历史：

```powershell
lark-cli apps +release-list --app-id <app_id> --as user
```

### 父仓库版本档案

`deployments/miaoda-app.json` 由父 Git 管理，只记录非敏感关联信息：

```json
{
  "app_id": "app_xxx",
  "local_path": "deployments/miaoda-app",
  "development_branch": "sprint/default",
  "last_verified_commit": "abcdef1",
  "last_release_id": "release_xxx",
  "status": "creator_only_validation"
}
```

不得写入 token、secret、临时 Git 凭据、Base URL 或真实业务数据。

`.json` 不是自动监控器，而是发布流程中的版本档案。每次验证或发布后必须同步更新；可增加只读校验脚本检查档案 SHA 是否等于 App Git 当前提交。

本地 App 目录丢失时，可根据档案里的 `app_id` 从妙搭远端重新初始化，不依赖父 Git 保存源码副本。

## 七、数据与安全边界

- 三个 Base 仍是唯一业务事实来源。
- 妙搭数据库不保存或镜像业务记录。
- Base 读取只申请满足需求的最小只读权限。
- Base URL、token、app secret、环境变量值不得进入源码、父仓库、App 仓库、文档或日志。
- 所有 Base 非空值保留规则、日期容错、字段别名、筛选和聚合口径必须与当前 `V1.2.0` 一致。
- 遗留问题以生成时间对应的 ISO 周为固定锚点，并通过日期减 7 天计算上一周；本地版与妙搭版只展示这两个标准周次，不从 Base 内容反推最新周。
- 会议纪律作为 `DashboardData.meetingDiscipline` 的会议内容数据维护，在线页和离线模板共用数据驱动渲染，HTML 不保存重复的硬编码正式文案。
- 会议内容解耦不改变视觉：继续使用原有会议专用类名，标题 `24pt／700`、正文 `15pt／400`、金额风险红色和联系人强调蓝色均保持不变，不与三个业务表格的 `16px` 规则合并。
- 迁移不得重新启用阶段快照 Skill，也不得依赖已删除的「阶段快照日期」字段。
- 刷新失败必须保留上一份成功数据并展示明确错误，不得用空数据覆盖页面。

### Base OpenAPI 约束

- 三张表使用同一个独立应用身份和同一套只读客户端，不混用用户 Token 或妙搭多维表格插件。
- 应用只申请满足记录查询所需的最小权限；代码只实现鉴权、读取视图／字段元数据和分页查询记录，不实现任何新增、更新或删除方法。
- Base 开启高级权限时，应用须按飞书要求获得足够权限；授权变化会直接影响看板读取，但不改变任何个人用户的角色。
- OpenAPI 返回的公式／Lookup 包装结构必须在中央取值函数中显式展开，并由自动化测试覆盖「阶段查找／状态查找」。
- 三个 Base URL、App ID 和 App Secret 只保存在环境变量中。开发环境绑定副本；正式切换只替换环境变量，禁止把 URL 或凭据提交到 Git。

## 八、开发期权限范围

开发与首轮验收期间：

- 不添加妙搭协作者。
- 不邀请其他操作者。
- 不扩大应用运行时可见范围。
- 应用保持仅创建者可见。
- 只验证创建者能够打开、读取、刷新、切换看板和下载快照。

下周团队验证时再单独执行：添加试点访问者、验证负责人独立操作、评估协作者角色和扩大可见范围。此阶段不提前实施。

## 九、实施阶段

### 阶段 0：规范和仓库边界

- 创建本文。
- 更新 `AGENTS.md`、`README.md`、`ROADMAP.md` 和 `.gitignore`。
- 创建妙搭 App 版本档案。

### 阶段 1：全栈 POC

- 创建 `full_stack` 应用并初始化独立仓库。
- 读取脚手架内插件指引。
- 验证副本中的「阶段查找／状态查找」可由 Base OpenAPI 返回。
- 配置独立飞书应用身份和三个副本 Base URL，验证服务端只读访问。
- 验证前端能调用服务端并显示明确成功／失败状态。

### 阶段 2：数据契约迁移

- 迁移三个 Base 的分页读取。
- 迁移字段映射、筛选、日期解析、最新段落和统计规则。
- 对比本地 `V1.2.0` 的关键计数、分组、警告和空值行为。

### 阶段 3：前端迁移

- 复用正式视觉 token、页面结构和会议纪律文案。
- 接入妙搭服务端刷新接口。
- 实现项目概况、详细进展、遗留问题和创新大赛视图。
- 提供按需下载的自包含离线 HTML。

### 阶段 4：创建者验收与发布

- 完成本地单元、构建和数据契约验证。
- 发布仅创建者可见版本。
- 验证页面访问、刷新、错误处理和离线下载。
- 记录 App commit SHA、release ID、线上链接和日志检查结果。

### 阶段 5：团队试点

本阶段延后至下周，由用户另行授权：

- 添加指定试点访问者。
- 验证普通使用者不需要本地环境即可使用。
- 评估添加管理者或开发者协作者。
- 验收后决定是否将妙搭版本升级为团队正式入口。

## 十、验收标准

开发期完成必须同时满足：

1. 应用创建者可打开发布后的页面。
2. 服务端不依赖本机 Python、启动脚本或 `lark-cli` 用户登录态。
3. 三个 Base 均通过只读链路读取。
4. 正式筛选、字段映射、统计和警告行为与 `V1.2.0` 对齐。
5. 页面能完成四个视图切换、PM 切换、刷新和全屏。
6. 刷新失败不会清空上一份成功数据。
7. Base URL、凭据和真实业务数据不进入 Git。
8. 离线快照可按需下载并在 `file://` 环境打开。
9. App Git 提交已 push 到 `sprint/default`。
10. 妙搭发布成功，父仓库档案与 `ROADMAP.md` 已记录对应提交和发布 ID。

## 十一、回退策略

迁移期间不删除、不覆盖当前本地 `V1.2.0`，同时保留 `V1.1.0` 模板：

- 妙搭尚未通过验收时，周会继续使用本地入口。
- 妙搭读取、权限或平台运行异常时，立即回退本地 `start-dashboard.cmd`。
- 妙搭迁移不得顺手修改本地业务规则；确需同步规则时先在父项目确认，再分别修改和验证两套实现。
- 团队正式切换前，不停止本地版维护，也不扩大妙搭可见范围。
