# 看板生成链路：架构说明与学习指南

> 面向第一次接触这套流程的读者，解释每个环节**是什么、为什么这么选、不这么选会怎样**，最后给出分层学习路线图。对应代码都在本项目 `src/` 下，建议对照阅读。

## 0. 一句话总览

这是「**本地工具型 Web 应用**」的最小形态：批处理做启动器，Python 标准库做后端，飞书 OpenAPI 做数据源，浏览器做界面——零第三方依赖、零部署、凭据不出本机。

```
双击 start-dashboard.cmd          ① 启动器（用户入口）
        │  设编码 → 设参数 → 调 python.cmd
        ▼
serve_dashboard.py                ② 本地后端  http://127.0.0.1:8710
        │  GET /          返回注入了数据的看板 HTML
        │  GET /api/data  触发一次全新数据拉取
        ▼
lark-cli 子进程 → 飞书 OpenAPI    ③ 数据通道（凭据托管在本机登录态）
        ▼
generate_dashboard.py             ④ 规则解析/匹配（业务核心，纯确定性代码）
        ▼
DATA JSON 注入 template HTML      ⑤ 模板渲染（单文件自包含）
        ▼
浏览器 hydrate() 渲染 + 交互      ⑥ 界面
```

## 1. 逐环节解剖：为什么这么做

### ① 为什么用 `.cmd` 做入口

**需求本质**：让使用者「双击即用」。Windows 上双击可执行、且无需安装任何东西的最低门槛就是批处理。

它只做三件事：设编码（`chcp 65001`，保证中文参数正确）、设参数（Base URL、lark-cli 路径、模板），然后把控制权交给 Python。**启动器不含任何业务逻辑**——这是刻意的，逻辑集中在 Python 里才可测试、可复用。

**替代方案为什么不选**：桌面快捷方式带不动长参数和注释；PowerShell 脚本默认执行策略禁止双击运行；打包成 exe 对一个内部 demo 过重。

**两个实际踩过的坑**（已记入全局规则）：批处理必须 CRLF 行尾（LF 会让 cmd.exe 解析错位）；URL 里的 `&` 必须在引号内（否则被当命令分隔符）。

### ② 为什么需要 Python 本地服务，而不是纯静态 HTML

先理解静态 HTML 的本质：**数据在生成那一刻被「烤」进文件，是快照**。快照的优点是单文件、发群里双击就能看；缺点是 PM 改了总表，页面不会变。

要实现「点按钮拉最新数据」，必须有一个**运行时**。为什么浏览器自己不行？两堵墙：

1. **凭据墙**：读飞书表需要访问令牌。令牌放进 HTML 就等于公开（红线）；不放又无权限。
2. **CORS 墙**：浏览器的同源策略禁止页面直接跨域调用飞书 API，飞书也不会为任意本地页面开白名单。

本地服务就是翻这两堵墙的**最小后端**：它跑在你的账号下（天然持有 lark-cli 登录态），暴露一个 `/api/data` 接口给页面。页面 fetch 的是同源的 `127.0.0.1:8710`，无 CORS 问题。

**为什么用标准库 `http.server` 而不是 Flask/FastAPI**：只有两个 GET 路由，框架的路由、中间件、模板引擎全用不上。零依赖意味着任何装了 Python 的机器直接跑，也意味着未来这层被公司平台后端替换时没有沉没成本。这是 YAGNI 原则（You Aren't Gonna Need It）的直接应用。

**`127.0.0.1` 的含义**：只监听本机回环地址，同一局域网的其他电脑无法访问——这本身就是一道安全边界，演示投屏时看板只在你的机器上。

### ③ 为什么经 lark-cli，而不是直接调飞书 API

lark-cli 底层调用的就是飞书标准 OpenAPI（`record-list` 等），它额外解决的是**凭据托管**：OAuth 令牌加密存在本机当前用户的登录态里，我们的代码从头到尾**不接触、不存储任何密钥**——代码可以放心入库、分享。

这也留好了演进接口：将来集成到公司平台时，把「lark-cli 子进程」换成「平台后端直接 HTTP 调 OpenAPI（应用身份）」，上下游的业务逻辑一行不用改——这叫**传输层可替换**。

工程细节：分页读取（每页 200 条）＋页间延时 0.2 秒，是为了避开飞书的频控限制。

### ④ 为什么用「规则代码」解析，而不是 AI

判断标准：**数据是否结构化、规则是否可枚举**。总表的字段名固定、日期格式可枚举、进展的书写约定明确（行首日期＋冒号分段、本周/下周标签），这类问题用正则和规则处理是 100% 确定性的——同样输入永远同样输出，可写回归测试，运行零成本。

AI 适合的是非结构化、有歧义的内容（比如把一段自由文本会议记录总结成风险要点）。在确定性问题上用 AI，反而引入不确定输出和推理成本。页面上「AI 正在汇总…」是产品演出，干活的是规则代码——**将来接入真 AI 总结时，规则层照样保留做数据准备**。

业务核心三块规则（都在 `generate_dashboard.py`）：

| 规则 | 做什么 | 关键点 |
|---|---|---|
| 层级匹配 | 白名单/字段筛选定位子任务 | 父 TDT record_id＋子任务名精确匹配，拒绝模糊匹配 |
| 里程碑状态机 | 每个节点判 done/late/pend | 有实际日期→done；无实际且计划早于今天→late |
| 进展解析 | 多日期块取最新、拆本周/下周 | 只认「行首日期＋冒号」为分段信号，行内日期不误切 |

### ⑤ 为什么「注入模板」，而不是前端启动后再拉数据

模板里有一个占位符：`let DATA = /*__DATA__*/null;`。生成时脚本把真实 JSON 替换进去，于是 HTML **单文件自包含**——不依赖服务也能打开。

这带来同一份模板的**双模式**能力（前端用 `location.protocol` 判断）：

- **file:// 双击打开**：用烤进去的快照数据＋模拟延时（可分发，脱离服务存活）；
- **http:// 服务托管**：点按钮真实 fetch `/api/data`，拿最新数据重渲染。

`hydrate()` 函数是这个设计的关键：把「数据 → 界面」封装成**可重入**的装配函数，首次加载调用一次，之后每次刷新再调用——同一套代码路径，不存在「首载逻辑」和「刷新逻辑」两套实现渐渐不一致的问题。

### ⑥ 前端还有一个不起眼但重要的细节：`esc()`

所有来自总表的文本在进入页面前都经过 HTML 转义。因为进展描述是 PM 手填的，理论上可能包含 `<script>` 之类内容——不转义就是 XSS 注入漏洞。**凡是渲染「别人输入的数据」，永远转义**，这是前端安全的第一课。

## 2. 这套架构的通用范式

记住这个模式，它可以复用到大量内部工具场景（报表生成器、数据核对工具、评审看板……）：

```
启动器(launcher) → 本地服务(local server) → 数据源(API) → 确定性转换(transform) → 单文件界面(single-file UI)
```

两个演进方向（本项目 ROADMAP 里都有）：

- **平台集成**：本地服务换成公司平台后端（按钮→后端→OpenAPI→JSON→渲染，结构同构）；
- **托管化**：部署到妙搭等托管平台，固定链接、打开即最新，摆脱对个人机器的依赖。

## 3. 知识路线图

按依赖顺序分五层，每层标注「在本项目中的锚点」——学完一个知识点就去对应文件里找它的用法，检验是否真懂。

### L1 地基（看懂启动器）
- **命令行与批处理**：环境变量、`%~dp0`、引号与转义、CRLF 行尾 → 锚点：逐行读懂 `start-dashboard.cmd`
- **HTTP 基础**：GET 请求、状态码（200/404/500）、Content-Type、localhost 与端口 → 锚点：说清 `/` 和 `/api/data` 的分工
- **JSON**：序列化/反序列化、和 Python dict / JS object 的对应 → 锚点：看懂 `output/*.report.json`

### L2 后端（看懂本地服务）
- **Python 标准库四件套**：`argparse`（命令行参数）、`subprocess`（调 lark-cli）、`http.server`（Web 服务）、`re`（正则） → 锚点：`serve_dashboard.py` 不到 150 行，通读
- **REST API 概念**：令牌、分页、频控 → 锚点：`scan_records()` 的分页循环
- 练习：给服务加一个 `GET /api/health` 路由，返回 `{"ok": true}`

### L3 前端（看懂界面）
- **CSS**：自定义属性（`--token` 变量，双配色/深浅色的实现基础）、grid/flex 布局、`position: sticky` → 锚点：改一个配色 token 看效果
- **JavaScript**：DOM 操作、事件监听、模板字符串、`fetch` 与 `async/await` → 锚点：解释 `hydrate()` 为什么能同时服务首载和刷新
- **安全**：XSS 与转义 → 锚点：`esc()` 被调用的每个位置

### L4 工程化（看懂为什么这样组织）
- **关注点分离**：启动层/数据层/展示层为什么拆成三个文件 → 检验：改「收录规则」只需动哪个文件？（答：`generate_dashboard.py`，模板与启动器零改动）
- **配置与数据的入库边界**：`.gitignore` 业务数据、example 占位文件模式 → 正式锚点：`dashboard_config.json` vs `dashboard_config.example.json`；旧白名单兼容格式单独保留在 `demo_scope.example.json`
- **可替换边界设计**：传输层（lark-cli↔OpenAPI）、展示层（demo1/2/3 共用数据层） → 检验：说出平台集成时哪些代码保留、哪些被替换

### L5 视野（演进方向）
- 飞书开放平台：应用身份、tenant_access_token、Base OpenAPI
- 部署形态对比：本地服务 / 定时任务＋推送 / 妙搭托管 / 平台内嵌
- AI 的正确切入点：确定性规则做数据准备，模型做非结构化总结

## 4. 建议的三个动手练习（由易到难）

1. **改参数**：用 `--port 9000` 启动服务，理解端口的含义；默认双击入口使用本项目专属端口段 `8710—8719`；
2. **加接口**：给 `serve_dashboard.py` 加 `/api/health` 路由（L2 检验）；
3. **加功能**：给看板增加「按项目阶段筛选」chips——你会被迫走通数据层（阶段字段已在 DATA 里）→ 模板渲染 → 事件绑定的完整链路，走完这条链，这套架构就真正属于你了。
